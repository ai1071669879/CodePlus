# 设计模式（26 种）

## 核心职责

在 C#/.NET 设计、重构与评审中，用**职责分配**的语言而不是模式名来解决问题：先写清"什么在变、谁不该知道什么"，再决定要不要引入模式。

本 skill 收录 26 种模式：创建型 6 + 结构型 8 + 行为型 12。它等于 GoF《设计模式》的 23 种加上 SourceMaking 目录中另外三种常被引用的补充模式：

| 补充模式 | 分类 | 为什么单独列出 |
| --- | --- | --- |
| 对象池 Object Pool | 创建型 | 解决"创建/销毁本身昂贵"，GoF 未收录 |
| 私有类数据 Private Class Data | 结构型 | 现代语言里多被 `readonly`/`init` 取代，列出以便识别"这是语言特性而非模式" |
| 空对象 Null Object | 行为型 | 多被可空引用类型 + `?.`/`??` 取代，只在需要多态默认行为时才值得 |

### 覆盖边界

只覆盖这套**经典面向对象模式目录**。架构型/企业型模式（Repository、Strangler Fig、Domain Events、Rules Engine、分层/微服务）与 agentic 编排模式（监督者/群体/流水线）**都不在范围内**——后者虽同名 "design patterns"，却属另一个领域，不要混用；也不做"182 个模式"式的枚举。

## 首要规则：模式不是起点

模式是对"语言/框架能力不足"的补偿。Lisp/Dylan 语境下 23 种 GoF 模式里有 16 种可以简化或消除（[SourceMaking：Design Patterns](https://sourcemaking.com/design_patterns)，引 Peter Norvig 的论证）。C# 同理：委托、泛型、`record`、`event`、`yield return`、LINQ、可空引用类型、DI 容器已经"消化"了一批模式。

这里要区分两件事：**采用某种设计意图**（用语言/框架的原生机制直接表达，成本低，就该用）与**新增手写类型与基础设施**（才需要额外的成本论证）。下表中间一列是"该意图的原生实现"——它**不是替代品**：用 C# `event` 实现观察者、用静态门面类实现外观，**就是在用这个模式**，只是没有手写一套类型体系。只有原生机制给不了你所需能力时，才值得手写类型。

| 你想要的效果 | 先用语言/框架的原生机制（这本身就是该模式的合法实现） | 只有原生机制给不了时，才手写类型 |
| --- | --- | --- |
| 可替换的算法/回调 | `System.Func<T>`、`System.Action<T>`、局部函数 | 算法自带状态，或有多个方法要一起变化（→ 手写策略类型） |
| 可空/缺省行为 | 可空引用类型、`?.`、`??` | 缺省行为必须是多态成员、由装配方统一决定（→ 手写空对象） |
| 不可变数据载体 | `readonly record struct`、`{ get; init; }` | 载体本身不该有模式（项目规则 R17） |
| 顺序遍历 | `yield return`、`System.Collections.Generic.IEnumerable<T>` | 需要多种遍历次序且必须隐藏内部结构（→ 手写迭代器） |
| 变更通知 | C# `event`、`System.IObserver<T>`——订阅、退订、广播语义都在，**这就是观察者** | 需要弱引用订阅、动态订阅集合，或跨进程投递 |
| 解耦创建 | DI 容器、构造函数注入 | 运行期才决定产品族/种类（→ 手写工厂类型） |
| 一次性简化子系统 | 一个静态门面类、或扩展方法——**这就是外观** | 子系统会有多套可替换实现，需要多态门面 |

## 工作流

1. **先描述问题，不要先说模式名。** 写出：变化的轴是什么、谁不该知道谁、当前代码在哪一处开始变难改。写不出这三句就不要选模式。
   - 如果手上只有一段粘贴的代码、拿不到仓库上下文（给不出 `文件:行号`）：仍然先写这三句，但把结论降级为"候选方案"并标注**未经仓库核实**；不要为了凑出位置证据而假定调用点数量。
2. **用选型表缩小候选。** 读取 [模式选择与反模式](references/pattern-selection.md)，从「变更轴」和「代码症状」两列各查一次、取交集；两列冲突或交集为空时按该文件的「冲突裁决」处理（默认以「变更轴」列为准）。
3. **读候选模式的完整条目。** 按分类读取 [创建型](references/creational-patterns.md) / [结构型](references/structural-patterns.md) / [行为型](references/behavioral-patterns.md)；逐条核对条目里的**适用条件**是否可观察地成立、**不要用于**是否命中——命中任一条就放弃该模式，不要把条件改到成立。
4. **先查仓库已有实现。** 新增抽象前按项目规则 R4 搜索同目录、同模块 `internal` 成员与被引用程序集公开面，命中就提可见性复用，不要复制一份。
5. **算代价。** 逐个回答：这个模式新增了几个类型/文件？它替换掉的简单写法是什么？如果只是把一处 `switch` 换成 N 个类而 N 不增长，退回简单写法。
6. **先分流，再动作。** 请求是"评审/该用什么模式"时，本步止于书面结论与候选取舍，不改文件（R12）；请求是"重构"时才落地：示例与命名遵守项目代码规范（§2.4），完成后过一遍本文的完成检查与 `pattern-selection.md` 的「六、反模式与红线」。

## 输出契约（结论必须包含这些，缺一项就是没做完）

参照公开设计模式 skill 的共同做法，本 skill 的**任何**结论（评审意见或重构方案）都必须能逐项填出下面的槽位；填不出的槽位本身就是一个结论（说明证据不足）：

| 槽位 | 要求 |
| --- | --- |
| ① 问题陈述 | 用"变化的轴 / 谁不该知道谁 / 具体位置"三句写，不出现模式名 |
| ② 决策 | **恰好一个主模式**，或明确写「**不采用模式**」；补充模式只在不可或缺且不重复职责时才加，且必须说明它补的是什么 |
| ③ 最简单但落选的替代方案 | 明确写出"我考虑过直接用 X（`switch`/委托/可空类型/普通方法），为什么它不够" —— 不写这一项，评审无法判断是否过度设计 |
| ④ 被否决的邻近模式 | 列出最接近的 1-2 个模式及否决理由（哪条"不要用于"命中），避免下次重复讨论 |
| ⑤ 代价 | 新增类型/文件数、被替换掉的简单写法、运行期与调试成本 |
| ⑥ 未证明的部分 | 明确列出"哪些信号我没有证据"（例如调用点数量、分支增长趋势）；无位置证据时结论必须标注**未经仓库核实** |
| ⑦ 越界标记 | 若方案会改变公共行为、所有权，或超出本次请求范围，**回退请求授权**，不要静默扩大改动 |

定位一句话：**模式选择不是架构批准，也不等于正确性证明**；本 skill 输出的是"有依据的取舍"，不是"用了某个模式所以对"。

## 与项目规则的衔接（强制）

设计模式引入的是**层和间接**，因此它必须同时满足项目的抽象准入规则：

- **R3 抽象层准入**：新增类型需满足其一——① 已有第二处调用方；② 需要独立生命周期或在多处之间传递状态。只是"换个名字传参"的层一律判为无用层，模式化包装也算。
- **R5 一个关注点一个派发点**：观察者、责任链、中介者、命令分发都属派发，必须恰好一次；"两处都派发更保险"不是通过标准。
- **R10 设计未定的机制不要自造**：异常类型、状态位、重试策略一旦引入即为长期契约；未定就在目标位置留 `TODO(类别): 编号 — 触发条件`。
- **R11 失败路径可观察**：链尾无人处理、命令未匹配、能力缺失、装配错误必须留下诊断、日志或异常，禁止静默 `return`。**契约明确的正常无操作不受此约束**——空对象的默认实现（例如"不写审计"）本身就是它的语义。要分清的是"设计好的什么都不做"与"本该发生却没发生"：后者必须可观察；`IsNull`/`IsNoOp` 之类的判据只帮调用点区分，**不能替代** R11 要求的痕迹。
- **R17 不可变数据载体**：模式的参数对象、命令对象、快照（memento）如果本身就是管线工作项或 DTO，就用 `readonly record struct`（需要 `with` 时用 `record struct`），不要用可变 POCO。
- **R18 公开面最小化**：模式引入的接口默认 `internal`，仅跨程序集需要才 `public`。
- **R22 资源释放成对**：对象池、代理、享元持有资源时，所有权与释放责任必须在类型契约里写清，释放放 `finally`。
- **R6/R7 事实核实**：不得凭模式名或惯例推断某个 API 的行为；涉及具体类型/方法签名的断言要给出 `文件:行号`。
- **R27 运行证据**：模式改动后按最小范围到全解决方案的顺序编译与测试，结论照抄实际输出计数。

## 完成检查

- [ ] 能用一句话说明"变化的轴"，且不出现模式名。
- [ ] 已确认没有更简单的**原生机制**能表达同一意图；若用原生机制实现（如 `event` 做观察者、静态门面做外观），已说明这是有意的实现选择，而非"未采用该模式"。
- [ ] 已按 R4 搜索过仓库已有实现，复用了而不是复制了。
- [ ] 新增抽象满足 R3 的准入条件之一；不满足的部分已内联。
- [ ] 派发点唯一（R5），不存在"两处都发一次"。
- [ ] 失败路径可观察（R11）：链尾、未匹配、能力缺失、装配错误都有诊断或异常；**正常的无操作**已与失败路径区分开。
- [ ] 类型可见性最小（R18）；属于管线工作项或 DTO 的数据载体不可变（R17）。
- [ ] 模式的"代价与误用信号"与"不要用于"逐条对照过，未命中 `pattern-selection.md` 的「六、反模式与红线」。
- [ ] 主模式只有一个（或已明确写"不采用模式"），补充模式有不可或缺的理由。
- [ ] 已写出"最简单但落选的替代方案"与"被否决的邻近模式及理由"。
- [ ] 已列出未证明的部分；无位置证据的结论已标注未经仓库核实。
- [ ] 未命中"模式堆叠"与"按名字选模式"两条红线（见 `pattern-selection.md`）。
- [ ] 越界变更（公共行为、所有权、超范围）已回退请求授权，未静默扩大改动。
- [ ] 相关测试已运行且失败为 0，结论附实际输出计数。
