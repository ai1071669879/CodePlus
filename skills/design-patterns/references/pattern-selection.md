# 模式选择与反模式

本文件把 26 种模式当成一个**可检索的决策库**，而不是待办清单。顺序是：先写问题，再查表，最后才选模式。

## 一、先回答三个问题

选模式之前必须能写下这三句，写不出就说明还在"模式先行"：

1. **变化的轴是什么？** 哪个维度会增长——产品种类、算法、状态、处理步骤、操作、交互方？
2. **谁不该知道谁？** 期望的依赖方向是什么，现在是谁在直接引用谁？
3. **现在最难受的具体位置在哪？** 给出文件与方法；说不出位置，就还没有"已经出现的问题"，此时引入模式属于投机性泛化。

### 冲突裁决与降级路径

- **两张表冲突时**（同一现象在「变更轴」与「代码症状」下给出不同首选）：以「变更轴」列为准。它描述的是"这个维度会不会继续变"，而症状表只描述"现在难看"。两表都指向同一模式时才算强候选；两表交集为空时同样回到「变更轴」列。
- **拿不到仓库上下文时**（只有一段粘贴的代码，给不出 `文件:方法`）：结论降级为**候选方案**并标注"未经仓库核实"，不要为了让判据成立而假定该 `switch` 已在多处重复——"多处重复"必须真的数过。
- **"多处重复"必须给出次数与位置**：只在一处出现时，一律先按第六节的「一次性抽象」红线处理。
- **证据强度排序**（取值从强到弱，只能引用你真正拿到的那一档）：① 真实代码或 diff 的 `文件:行号` → ② 类型/契约/伪代码 → ③ 文字描述。用第 ③ 档得出的结论一律标注为未核实。
- **不许靠"看起来像"产生信号**：不能因为"这段代码长得像策略模式"就断言存在变化压力；每个信号都要能指回上一条里的某一档证据。
- **反过来记录"没有证明的部分"**：明确列出"哪些信号我拿不到证据"（调用点数量、分支增长趋势、并发上限、状态迁移频率）。缺了这份清单，结论必然从"有依据的取舍"滑向"全面处方"。

### 定位候选：按问题类别下钻

先判断问题属于哪一类，再进第三节的表；**三类都不属于时，很可能根本不该用模式**。这一步只产生候选，不能替代第三节的变更轴判据与各模式的"不要用于"。

- **问题在"对象怎么来"？→ 创建型**
  - 只有一种实现 / 调用点已知具体类型 → 不用模式（直接 `new`）
  - 产品种类会增长、调用方不该知道具体类 → 工厂方法
  - 多个产品维度、必须保证同族一致 → 抽象工厂
  - 构造参数多且有必填/可选组合 → 建造者
  - 构造昂贵，或要保留运行时配置快照 → 原型
  - 创建昂贵、可安全重置、并发上限明确 → 对象池
  - 全进程唯一且无自然宿主 → 单例（先问"能不能交给 DI 容器管生命周期"）
- **问题在"对象怎么组合、怎么访问"？→ 结构型**
  - 接口不兼容且事后才发现 → 适配器
  - 两个维度各自独立演化（M x N 类爆炸） → 桥接
  - 树的"部分-整体"要统一处理 → 组合
  - 能力按幂集叠加、需要运行期组合 → 装饰器
  - 多步编排要收成单一入口 → 外观
  - 内存被大量重复的不可变数据占满 → 享元
  - 构造后要收窄数据写权限，且确需数据与方法的物理分离 → 私有类数据
  - 要控制对同一对象的访问（延迟/权限/远程/计数） → 代理
- **问题在"职责与通信怎么分配"？→ 行为型**
  - 多个候选处理者、顺序或集合可配置 → 责任链
  - 请求要被排队/记录/重放/撤销 → 命令
  - 小型规则语言需要求值（且文法稳定） → 解释器
  - 需要隐藏集合内部结构或提供多种遍历顺序 → 迭代器
  - N 方互相引用、交互规则要集中 → 中介者
  - 需要快照/回滚且不能破坏封装 → 备忘录
  - 缺省行为需要参与多态分发 → 空对象
  - 发布方不该知道订阅方、订阅集合动态 → 观察者
  - 行为随状态变化且状态多、迁移频繁 → 状态
  - 同一契约下多种算法、需运行期选择 → 策略
  - 多个实现共享固定算法骨架 → 模板方法
  - 元素类型稳定、操作持续增加 → 访问者

## 二、GoF 的二维分类：范围 x 目的

| 范围 \ 目的 | 创建型 | 结构型 | 行为型 |
| --- | --- | --- | --- |
| **类模式**（用继承把变化固定在编译期） | 工厂方法 | (类)适配器 | 解释器、模板方法 |
| **对象模式**（用组合/委托把变化推到运行期） | 抽象工厂、建造者、原型、单例、对象池 | 适配器(对象)、桥接、组合、装饰器、外观、享元、私有类数据、代理 | 责任链、命令、迭代器、中介者、备忘录、空对象、观察者、状态、策略、访问者 |

判定要点：**优先对象模式**。类模式把变化点写在类型集合里，一旦集合变化就要新增/修改子类；对象模式把变化点放在运行期可替换的协作者上。只有当"变化的确实是编译期已知的一组类型，且它们共享算法骨架"时，类模式（模板方法、工厂方法）才更直接。

## 三、按"变更轴"选型

| 会变化的东西 | 首选 | 备选 | 什么时候不用 |
| --- | --- | --- | --- |
| 算法/策略 | 策略 | 模板方法、委托 `System.Func<T>` | 算法无状态且只有一个方法签名：直接用委托 |
| 同一对象的内部状态 | 状态 | 枚举 + `switch`、策略 | 状态少且无迁移：保留 `switch` |
| 具体产品类型 | 工厂方法 | 抽象工厂、DI 容器 | 只有一种实现：`new` |
| 一整套相关产品族 | 抽象工厂 | 多个工厂方法 + 注册表 | 产品族只有一个维度：工厂方法 |
| 复杂对象的构建步骤 | 建造者 | 构造函数 + 可选参数、对象初始化器 | 参数少于 4 个：别上建造者 |
| 对象的来源（新建/复制/池化） | 原型、对象池 | 单例 | 对象便宜且无状态：不要池 |
| 接口不兼容的外部实现 | 适配器 | 外观 | 可以改对方接口：直接改 |
| 抽象与实现两个维度 | 桥接 | 策略 + 工厂 | 只有一个维度变化：策略足够 |
| 树形部分-整体结构 | 组合 | 手工递归 + 类型判断 | 结构固定且只有两层：别抽象 |
| 可叠加的横切职责 | 装饰器 | 中间件/管道、AOP | 职责固定且只有一种组合：直接写在方法里 |
| 子系统的使用方式 | 外观 | 门面函数、扩展方法 | 调用方本来就只需要一步：扩展方法 |
| 细粒度对象的内存占用 | 享元 | 缓存、不可变值对象 | 状态可变：共享会引入竞态 |
| 对象数据的可见范围 | 私有类数据 | `readonly`、`init`、不可变 record | 语言已能表达：用语言特性 |
| 对目标对象的访问 | 代理 | 装饰器 | 目的是加职责而非控访问：装饰器 |
| 请求的处理者集合与顺序 | 责任链 | 管道/中间件、策略列表 | 只有一个处理者：直接调用 |
| 请求本身（排队/记录/撤销） | 命令 | 闭包/委托、消息队列 | 不需要排队/重放/撤销：委托即可 |
| 小型规则文法的解析 | 解释器 | 表达式树、`System.Linq.Expressions`、脚本引擎 | 文法固定且简单：直接写解析函数 |
| 集合的遍历方式 | 迭代器 | `yield return`、`System.Collections.Generic.IEnumerable<T>` | 语言已能表达：用 `yield` |
| 多对象之间的交互 | 中介者 | 事件总线、观察者 | 只有两方：直接引用 |
| 对象状态的快照与恢复 | 备忘录 | 不可变对象 + 整体替换、序列化 | 状态大到无法整体保存：只存增量 |
| 缺省/无操作行为 | 空对象 | 可空引用类型 + `?.`/`??` | 缺省行为不需要多态：用可空类型 |
| 状态变更的广播 | 观察者 | C# `event`、`System.IObserver<T>`、消息总线 | 订阅方需要弱引用或动态集合：手工实现订阅表 |
| 继承层级组合爆炸 | 装饰器、桥接、策略 | 组合 + 委托 | 组合数小于 4：扁平枚举更清楚 |

### 从 `if`/`switch` 链升级为策略或状态：检查信号（不是准入条件）

定性词（"分支很多""频繁变化"）不足以决策；下面四条也**不是必要条件**，而是**检查信号**——命中的越多，模式越可能划算；一条都不命中，通常说明 `switch` 或字典就够了。**是否真的新增类型，最终由三件事决定**：职责归属（这段逻辑是否属于一个独立协作者）、状态归属（变化的状态是否属于对象自身）、实际变化压力（是否已经在为它改代码），并受项目规则 R3 的抽象准入约束。

| # | 检查信号 | 命中说明什么 | 不命中也不能否证 |
| --- | --- | --- | --- |
| ① | 同一组分支逻辑出现在 **≥2** 个方法或类型里 | 抽出去能消除重复；只在一处时多一层间接（触发第六节的「一次性抽象」红线） | 只有一处，但该逻辑有独立生命周期、需要被注入替换时，R3 的第二个条件仍然成立 |
| ② | 分支数 **≥5**，且最近几次改动是"**新增**分支" | 变化压力真实存在 | 分支数少但单个分支很重时，数量不是关键 |
| ③ | 至少一个分支内部是**非平凡算法**（超过约 10 行，或自带状态、依赖、资源） | 行为值得独立成类型 | 分支都只是赋值/转发时，多态只增加文件数与跳转 |
| ④ | 选择发生在**运行期**（配置、插件、测试替身、按 Provider 路由） | 多态有收益 | 选择在编译期确定、但类型有独立生命周期时，R3 仍允许拆分 |

**与状态模式判据的统一**：行为型参考文件对状态模式写的是"状态数仍在增长 / 状态相关代码频繁变化 / 同一状态的行为散布在多个方法中，**任一为是就值得考虑**"。两者口径一致——都是**信号**：任一命中就值得**考虑**，全部不命中才倾向 `switch`。若某处写成"四条全部成立才允许升级"，那是把经验数字误当成了准入条件；数字可由团队按自己的代码库调整，**信号口径与"以 R3 和实际变化压力定夺"这一点不可改**。

上述数字是工程经验，不是 SourceMaking / Refactoring.Guru 的原文结论——那两个来源对这一点只给定性描述。与项目规则冲突时，以 `AGENTS.md` §2 的规则为准。

## 四、按"代码症状"选型

从症状出发比从模式名出发可靠得多。左列必须是**可观察的现象**。

| 症状（可观察） | 候选模式 | 对应的重构手法 |
| --- | --- | --- |
| 同一 `switch`/`if` 链在多处重复，分支随类型增长 | 策略、状态 | Replace Conditional with Polymorphism |
| 构造函数参数长且多为可选组合 | 建造者 | Introduce Parameter Object |
| 调用方要写 5 步以上编排才能完成一次用例 | 外观 | Extract Method + Move Method |
| 一类对象里大量字段只在某些状态下有效（Temporary Field） | 状态 | Replace Type Code with State/Strategy |
| 集合的内部结构（数组、索引、游标）泄漏给调用方 | 迭代器 | Encapsulate Collection |
| 空值检查散落在每个调用点 | 空对象 | Introduce Null Object |
| 一处业务改动需要同时改 N 个文件（Shotgun Surgery） | 中介者、观察者 | Move Method + 引入中介 |
| 两个类型互相直接引用，形成环 | 中介者 | Hide Delegate |
| 子类数量按维度相乘增长（M x N 个类） | 桥接、装饰器、策略 | Replace Inheritance with Delegation |
| 内存被大量结构相同的小对象占满 | 享元 | Change Value to Reference |
| 每次使用都要重建昂贵对象（连接、句柄、缓冲区） | 对象池、原型 | — |
| 需要在对象之外保存状态以支持撤销/重放 | 备忘录、命令 | — |
| 需要在不动元素类的前提下持续新增操作 | 访问者 | — |
| 请求需要按可配置的顺序交给多个候选 | 责任链 | — |
| 每次改算法都要改调用方 | 策略 | Replace Conditional with Polymorphism |
| 多个实现共享固定步骤但细节不同 | 模板方法 | Form Template Method |
| 一个方法同时做多件事（校验、搬运数据、派发、写日志） | **不用模式** | Extract Method + Move Method：先拆方法；这一步用不上任何模式 |

## 五、常见模式组合

以下组合在公开文献里被反复描述（见 Refactoring.Guru 各模式页的 *Relations with Other Patterns* 小节与 GoF 的 *Related Patterns*）。**它们是线索，不是必须遵守的规则**；是否采用仍按第一节的三个问题判断。

| 组合 | 为什么常一起出现 |
| --- | --- |
| 抽象工厂 + 工厂方法/单例 | 产品族需要一个全局注册入口 |
| 建造者 + 组合 | 递归地构建树形结构 |
| 组合 + 迭代器 + 访问者 | 树结构：统一处理、遍历、操作分离三者配套 |
| 装饰器 + 组合 + 策略 | 包装同一接口并叠加职责 |
| 命令 + 备忘录 | 可撤销命令（命令持快照） |
| 命令 + 责任链 | 请求沿链转交或排队 |
| 观察者 + 中介者 | 中介负责协调，通知通过订阅扩散 |
| 策略 + 工厂方法 | 按 key 选择算法实现 |
| 状态 + 享元 | 状态对象自身无数据时可共享实例 |
| 模板方法 + 工厂方法 | 骨架中的创建步骤交给子类实现 |
| 适配器 + 外观 | 统一旧接口，同时简化调用编排 |
| 代理 + 享元 | 共享对象的访问控制与延迟加载 |

## 六、反模式与红线

| 反模式 | 识别信号 | 改法 |
| --- | --- | --- |
| 模式先行 (pattern-first) | 先说出"这里要用策略模式"，再去找变化点 | 回到第一节三个问题，写不出就不引入 |
| 一次性抽象 | 接口只有唯一实现、唯一调用点（违反 R3） | 内联；等第二处调用方出现再抽 |
| 层间一一对应 | 两个类型字段逐一对应，只是换了名字 | 合并；抽象必须携带行为差异 |
| 抽象通货膨胀 | 一个功能引入 5 个以上的新类型 | 数一下新增类型数，超过问题规模就是过度设计 |
| 金锤子 (golden hammer) | 所有问题都用同一个熟悉的模式解 | 按第三节变更轴重新选型 |
| 上帝对象 (God Object) | 一个类承担创建、编排、通知、持久化 | 按职责切分；创建交给工厂，交互交给中介 |
| 上帝方法 (God Method) | 一个方法里同时做校验、搬运数据、派发与日志 | 先 Extract Method 拆方法；这一步用不上任何模式，别用模式掩盖职责混杂 |
| 收容所类 | `XxxManager`/`XxxHelper`/`XxxUtil` 里堆满无关静态方法 | 按变更轴归类到具体协作者 |
| 投机性泛化 (speculative generality) | 为"以后可能要支持"插入扩展点 | 删掉；扩展点只在第二个实现出现时加 |
| 服务定位器 (Service Locator) | 在类内部向容器/全局注册表索取依赖 | 改为构造函数注入，依赖显式化 |
| 静默失败 | 链尾无人处理、未匹配分支、能力缺失或装配错误直接 `return`（违反 R11） | 写诊断、记日志或抛异常；**契约明确的正常无操作不算**，但要在装配点与失败区分开 |
| 双重派发 | 同一事件在两处各派发一次，"更保险"（违反 R5） | 确定唯一派发点，断言恰好一次 |
| 伪装饰器 | 装饰器内部开始做业务判断，或改变了输入语义 | 装饰器只叠加职责；业务判断回到被装饰者或策略 |
| 单例即全局可变状态 | 单例持有可写字段，被多处修改 | 单例只持不可变配置；可变状态交给显式传入的对象 |
| 共享可变享元 | 被共享的实例含可变字段 | 内在状态必须不可变；可变部分外置为参数 |
| 注释代替命名 | 用注释解释"这是哪个模式" | 用领域名命名类型，注释只写约束来源（R20） |
| 模式堆叠 (pattern stacking) | 同一处同时上工厂 + 建造者 + 代理 + 单例，只为"结构完整" | 最多一个主模式；补充模式必须说明它补上了哪条没有它就闭合不了的职责 |
| 货物崇拜 (cargo cult) | 照着样板抄模式结构，说不清它解决本项目哪个问题 | 回到第一节三个问题；说不出具体问题就删掉 |
| 按名字选模式 | "这里应该用策略模式"——理由是名字听起来合适 | 用问题类别与变更轴判据选，不用名字匹配 |

## 七、评审清单（评审他人设计时逐条过）

- [ ] 能用一句话说出变化的轴，且这句话里不出现模式名。
- [ ] 模式解决的是**已经出现**的问题，而不是预期问题（有具体文件与方法为证）。
- [ ] 已确认语言/框架特性无法更简单地解决。
- [ ] 新增抽象满足项目规则 R3 的准入条件之一，不存在"唯一实现 + 唯一调用点"的接口。
- [ ] 派发点唯一（R5），且断言验证的是"恰好一次"而不是"至少一次"。
- [ ] 失败路径可观察（R11）：链尾、未匹配、能力缺失、装配错误都有痕迹；**正常的无操作**已与失败路径明确区分（不把设计好的 no-op 当失败，也不让失败借 no-op 藏起来）。
- [ ] 属于管线工作项或 DTO 的数据载体不可变（R17）；接口可见性最小（R18）。
- [ ] 持有资源的模式（对象池、代理、享元）写清了所有权与释放责任（R22）。
- [ ] 已按 R27 跑过受影响模块的最小编译、相关测试与全解决方案编译，结论照抄实际输出计数；未执行的项标注为未执行。
- [ ] 结论里**恰好一个主模式**，或明确写了「不采用模式」。
- [ ] 已写出"最简单但落选的替代方案"，以及被否决的邻近模式与理由。
- [ ] 已列出"没有证明的部分"；无位置证据的结论标注了未经仓库核实。
- [ ] 会改变公共行为、所有权或超出请求范围的方案已回退请求授权，未静默扩大改动。
- [ ] 类型用**领域名**而不是模式名（`ExportDescriptorFactory` 优于 `BuilderManager`）。
- [ ] **删除测试**：删掉一半新增类型后行为不变，说明另一半是过度设计。

## 八、与设计原则的对应（常见解读，非权威判据）

| 原则 | 主要由哪些模式体现 | 说明 |
| --- | --- | --- |
| 单一职责 | 外观、中介者、命令 | 把"编排/协调/请求表示"从业务对象里挪走 |
| 开闭原则 | 策略、装饰器、观察者、工厂方法 | 新增行为靠新增类型，而不是修改已有分支 |
| 里氏替换 | 组合、模板方法 | 子类型必须能被基类型替换，否则继承关系本身就是错的 |
| 接口隔离 | 适配器、访问者 | 按使用方需求切分接口，而不是给一个胖接口 |
| 依赖倒置 | 工厂方法、抽象工厂、桥接 | 高层模块依赖抽象，创建细节落在低层 |
| 迪米特法则 | 外观、中介者、代理 | 只与直接协作者对话，不穿透对象链 |
| 组合优于继承 | 装饰器、桥接、策略、责任链 | 把编译期的类层次换成运行期的对象组合 |

这些对应关系在不同教材里表述不完全一致；把它当**沟通用的启发**，不要当成"用了某个模式就等于满足了某条原则"的证明。

## 九、对设计模式本身的合理怀疑

SourceMaking 在同一目录里明确列出了对模式的批评，值得在选择前读一遍：

- **解决的是错的问题**：模式的需求来自语言抽象能力不足。Paul Graham 的 *Revenge of the Nerds* 与 Peter Norvig 的论证指出，GoF 23 种里 16 种在 Lisp/Dylan 中可以被简化或消除。→ C# 里对应的检查就是本文第二节的"先试语言/框架能力"表。
- **缺乏形式化基础**：模式的分类是经验性的，不是可证明的规约。
- **导致低效方案**：模式常被当成"够用就行"的模板直接套用，而不如一次设计良好的分解。
- **与其他抽象形式差别不大**：MVC 等"模式"早于设计模式概念出现。

结论性判断：**模式的价值在于共享词汇与已支付的试错成本，而不在于它本身更正确。** 当模式与更简单的分解冲突时，选更简单的分解。
